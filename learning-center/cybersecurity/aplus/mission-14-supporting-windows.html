Supporting Windows

Isolate connectivity and performance problems before choosing a recovery action.

14.1 • Diagnose connectivity by layer

Check link state first, then IP configuration, default gateway, name resolution, and the application. A 169.254 address on a DHCP client suggests it could not obtain a lease. A reachable approved IP with failed hostname lookup points toward DNS. Use ipconfig /all for configuration, nslookup for DNS answers, and tracert for path clues. ICMP may be filtered, so corroborate a timeout with an application-level test.

14.2 • Authorized remote support

Quick Assist and other screen-sharing tools can let a user observe and approve a support session. RDP supplies remote desktop access; WinRM and SSH support remote administration; RMM offers managed monitoring and support; SPICE can provide a VM console. Use an approved channel, verify identity, obtain consent, and record actions. Avoid exposing remote administration directly to the public internet.

14.3 • Performance and recovery

Task Manager shows immediate process and resource use; Resource Monitor helps identify which process is doing disk or network I/O. Performance Monitor records counters over time, while Event Viewer helps correlate failures to timestamps. If Windows stops booting after a change, use approved Windows Recovery Environment options such as Startup Repair, Safe Mode, uninstall updates, or System Restore when available. Account for encryption recovery and data protection before reset or reimage.

14.4 • Separate profile, app, and startup faults

Compare another approved test profile and another launcher or app version. An issue isolated to one profile points toward that profile or its per-user settings. If an issue reproduces only under normal startup, use an approved selective startup procedure to narrow conflicting third-party items and restore the prior configuration after testing.

Interpret network test results

The Ethernet link is up. The gateway responds. The approved file service is reachable by address, while nslookup for its name returns NXDOMAIN. Check the spelling, configured DNS resolver, and expected DNS record with the service owner. After correction, repeat the name lookup and open the share by its approved name.

Technician case file

A PC became unstable after a driver update and now repeatedly fails to boot. Another similar PC is healthy.

Write a short ticket in your study notebook. Include the evidence, your first action, and how you will verify the result. Use fictional details for this case.

Compare your ticket with the model response

Record the change and boot symptoms. Confirm backup and recovery-key availability, use WinRE and an approved rollback or restore option, then verify normal startup, affected device function, and user workflow before closing the ticket.

Check that your ticket uses the scenario’s clues, explains the action in order, and specifies what a passing verification looks like.

Practice and readiness check

Choose the best answer for each question. Explain which clue supports your choice. The final question continues the technician case.

The gateway responds and an approved service works by IP but fails by hostname. Which test fits?
Explanation

Name lookup isolates DNS after basic IP reachability is established.

A user needs to observe each step during a guided help-desk session. Which approach fits?
Explanation

A consent-based screen-sharing session allows the user to follow the work.

A service crashes daily at 13:00. What evidence should you gather first?
Explanation

Time-correlated logs help identify the fault and distinguish it from system-wide failures.

Only one user's profile fails to load. Which test narrows the scope?
Explanation

The test distinguishes profile-specific behavior from a system-wide login issue.

Startup succeeds after a rollback. What evidence best supports closure?
Explanation

Verification should reproduce the previously failing workflow and confirm the fix persists.
